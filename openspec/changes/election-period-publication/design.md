## Context

2026 年地方公職人員選舉在 2026-11 舉行，現在是 2026-08。

`docs/規劃-2026地方選舉.md`（2026-08-18，經 Codex 與 Antigravity 各一輪覆核）
定案了一套分階段發布規則。兩個覆核者的共識包括：現有中立性需求不足以涵蓋選舉
期間的發布、且**應另立需求**；以及「選前只做歷史比較安全」的推論站不住。
兩者的分歧是 Antigravity 主張選前完全擱置、Codex 主張按資料性質分階段，
該文件採用了 Codex 的切法。

**那套規則從未寫進本 repo。** 現有八個能力、60 條 Requirement 中，
發布類的只有「個資不輸出」與「立委與地方資料分開發布」，沒有任何一條談時序。
規則只存在於一份狀態為「構想，未進入 Spectra」的文件，而該文件的「本站」
指的是相鄰的 `indigenous-constitution-tw`——本 repo 的讀者沒有理由把它當成自己的約束。

其後果已經發生：2026-08-23 上線的 `docs/legislative.html` 第四節呈現
不分區政黨票的界限估計（2008-2024 五屆，Duncan-Davis），發布時沒有任何
書面規則可供對照判斷它該不該在選前上線。

使用者已於 2026-08-23 對該區塊做出判定：**留著、加註不代表本屆、凍結**。
本設計把那個判定連同它所依據的規則一起寫成可檢查的東西。

## Goals / Non-Goals

**Goals:**

- 把分階段規則寫成 Requirement，使「現在可不可以發布這個」有書面答案
- 給出「解讀性指標」與「已凍結的歷史數據」的**可判定**判準，
  而不是留給當下的直覺
- 對既有三頁逐頁判定並留下紀錄，含理由與日期
- 讓「新增一頁卻沒有判定」與「判定為歷史數字卻沒有標示」**都會使測試失敗**

**Non-Goals:**

- 不改任何資料、不重建任何長表、不重算任何數字
- 不移除 `docs/legislative.html` 的任何區塊（使用者已判定留著）
- 不建立選情追蹤、預測或候選人導向的任何東西——那是規則要擋的對象本身
- 不處理相鄰 `indigenous-constitution-tw` 的發布規則。本變更只約束本 repo，
  即使規則的來源文件談的是那一邊
- 不定義地方層級的代表性指標（README「尚未解決」第 2 點）。
  依本規則它屬選前不得新增的解讀性指標，時機未到

## Decisions

### 決策 1：階段界線由**宣告值**決定，且未查證時從嚴

規則有三段：選前／選舉期間／正式結果確認後。要判定「現在是哪一段」就需要日期。

**2026-08-23 查證結果（中選會第 622 次委員會議通過的工作進行程序表）：**

| 事項 | 日期 |
| --- | --- |
| 選舉公告發布 | 2026-08-20 |
| 候選人登記 | 2026-08-31 至 09-04 |
| 公辦政見發表會 | 2026-11-13 起 |
| 投票、開票 | **2026-11-28（星期六）** |
| 審定並公告當選人名單 | 2026-12-04 前 |

⚠️ **這推翻了本變更提出時的前提。** 提案寫「現在是選前」，但選舉公告已於
2026-08-20 發布——`docs/legislative.html` 是 2026-08-23 上線的，
**在選舉程序開始之後三天**，不是選前。

**階段界線取「選舉公告發布日」，不取法定競選活動期間。**
兩個可選的界線：選舉公告發布（2026-08-20）與公辦政見發表會／競選活動期間
（2026-11-13 起）。取前者。理由是本規則要擋的是「數字被當成攻防素材」，
而候選人一登記、選戰的討論就開始了，不會等到法定競選期間才開始。
兩者相差三個月，取寬的那個等於這條規則在最需要它的三個月裡不生效。

因此本專案目前的階段是 **選舉期間**，至 2026-12-04 公告當選人名單為止。

**日期未查證時，一律視為選舉期間。** 這條在本次已不適用（日期查到了），
但作為規則保留：下一次選舉來臨時，查證前不會誤放行。
猜一個日期然後照它放行，是用看起來精確的數字掩蓋沒查證的事實——
本專案在 `EXPECTED_INDIGENOUS_ELECTORS` 上犯過同一類錯（四個值未經量測
就標成「普查值」）。誤攔截看得見（有人會來問為什麼不能發），誤放行看不見。

**替代方案**：以系統時間自動切換階段。否決——那會讓一個發布規則在無人
注意的情況下自己鬆綁，而放寬的那一刻正是最需要有人看著的時候。

### 決策 2：「解讀性指標」的判準是兩問，兩問皆是才算

一個數字是不是「解讀性指標」，逐條問：

1. **它是不是全查？** 值能否由已公告的官方票數逐票加總得到？
   不能（需要推估、外插、或跨母體相除）→ 指向解讀性。
2. **它有沒有方向？** 是否產生「落差」「不足」「傾向」「偏好」這類
   帶方向的量，而不只是一個計數或比率？

**兩問皆是 → 解讀性指標**；否則是歷史數據。

套用結果：立委的得票率、席次、投票率都是逐票全查、無方向 → 歷史數據。
政黨傾向界限需要推估、且產生「傾向」 → **解讀性指標**。

**替代方案**：以「是否來自官方檔案」為判準。否決——界限估計的每一個
輸入都來自官方檔案，這條判準會把它判成歷史數據，等於沒有判準。

### 決策 3：已判定為解讀性指標者，選前的處置是「保留＋標示＋凍結」

使用者於 2026-08-23 判定：`docs/legislative.html` 第四節留著。

依規則，選前允許「已凍結的歷史原始數據與固定的計算規則」。該區塊的五屆
都是已公告的官方結果、計算式寫定在版控裡、重跑得到同一個數，
因此在**已凍結**這一點上成立；但它是解讀性指標，所以另外兩件事必須到位：

- **標示**：明文寫出它是歷史數字、不代表 2026 本屆結果
- **凍結**：正式結果確認前不新增任何指標，包含不加屆別、不加門檻、不加政黨

**替代方案**：選前整節撤下。使用者已否決；且覆核採納的是 Codex 的切法，
Codex 明文反對機械延後。

### 決策 4：判定紀錄是一份表，且**每一頁都必須在表裡**

紀錄放在 `docs/發布判定紀錄.md`，逐頁一列：頁面、內容類別、判定、理由、判定日期。

要守的不變量是**涵蓋**而不是內容：`docs/` 下每一個 `.html` 都必須在表裡有一列。
新增一頁而沒有判定 → 檢查失敗並具名該檔名。

理由：這條檢查真正要擋的不是「判定寫錯」（那需要人看），
而是「多了一頁，沒有人想起要判定」。後者是靜默的，而且會隨時間必然發生。

**替代方案**：把判定寫在各頁的 HTML 註解裡。否決——那樣就沒有一個
地方能一眼看出「有沒有漏掉哪一頁」，而漏掉正是要擋的東西。

### 決策 5：標示的檢查比對**具名字串**，不是「有沒有提到 2026」

標示的檢查斷言頁面含一段固定措辭，且該措辭只有這個用途會出現。

理由：`docs/legislative.html` 本來就含「2026」（頁尾的更新日期 `更新：2026-08`）。
用「有沒有提到 2026」當判準，這條檢查在標示被刪掉之後**照樣通過**——
那正是本專案在變異測試上反覆踩到的「斷言的是別的東西」。

## Implementation Contract

**Behavior（做完之後看得到什麼）**

- `docs/legislative.html` 的政黨傾向區塊內含一段明文：本節為 2008-2024 的
  歷史數字，不代表 2026 年本屆選舉結果。該段落與數字在**同一個可複製的區塊**內，
  與既有的涵蓋率限定語同一處理方式。
- `docs/發布判定紀錄.md` 存在，宣告投票日（含來源或標為未查證）與目前階段，
  並逐頁列出 `docs/` 下每一個 HTML 的判定。
- `README.md`「發布上的限制」由兩條擴為三條，第三條是時序規則並指向紀錄檔。
- `docs/規劃-2026地方選舉.md` 頂端加一段狀態說明：其「下一步」第 1-3 項
  在本 repo 已完成，文中的「本站」指相鄰 repo，其分階段規則已於本變更
  寫入本 repo 的 spec。

**Interface / data shape**

- 紀錄檔的逐頁表欄位固定為：`頁面`、`內容類別`、`判定`、`理由`、`判定日期`。
- 標示的具名字串宣告為 `scripts/build_site_data.py` 的模組層常數
  `CURRENT_TERM_NOTICE`，頁面與檢查兩邊都用它，不各寫一份。

**Failure modes（都必須中止並具名，不得靜默）**

- `docs/` 下有 HTML 未出現在紀錄表 → 失敗，訊息含該檔名
- 紀錄表列出的頁面在 `docs/` 下不存在 → 失敗，訊息含該檔名（兩個方向都驗）
- 判定為「含歷史選舉數字」的頁面缺少 `CURRENT_TERM_NOTICE` → 失敗，訊息含該頁名
- 紀錄檔缺少投票日欄位 → 失敗；投票日標為未查證時，階段須為選舉期間，
  否則失敗

**Acceptance criteria**

- `pytest scripts/test_build_site_data.py` 通過，且新增檢查不少於 8 項
- 變異測試新增四項且全部被偵測到：
  1. 從紀錄表刪掉 `legislative.html` 那一列
  2. 從 `docs/legislative.html` 移除 `CURRENT_TERM_NOTICE`
  3. 把標示的檢查改成比對「2026」而非具名字串
     （此項須**仍能通過基準、但在第 2 項變異下漏網**，證明決策 5）
  4. 投票日標為未查證時把階段寫成選前
- `python scripts/build_site_data.py --check` 仍三頁全綠、既有屆別逐鍵重現

**Scope boundaries**

- 在範圍內：上述四個檔案的內容、`scripts/build_site_data.py` 的常數與檢查、
  `scripts/test_build_site_data.py` 與 `scripts/mutate_build_site_data.py` 的擴充
- 不在範圍內：任何長表的重建、任何數字的重算、`docs/index.html` 與
  `docs/roster.html` 的內容（它們只需要在紀錄表裡有一列）

## Risks / Trade-offs

**風險一：這是一份自己管自己的規則，沒有外部強制力。**
檢查只能驗「紀錄表涵蓋每一頁」與「該標示的有標示」，驗不了「判定是對的」。
判定對不對需要人看。接受這個限制，並在紀錄表要求寫下理由與日期——
理由寫不出來，本身就是訊號。

**風險二：預設從嚴會擋到無害的東西。**
投票日未查證期間，任何新的解讀性指標都會被規則擋下。這是刻意的取捨：
誤攔截看得見（有人會來問），誤放行看不見。

**風險三：標示可能被讀成免責聲明而失效。**
一段「不代表本屆」的小字，讀者可能整段略過。這條規則不宣稱能防止誤讀，
它只保證**限定語與數字在同一個可複製的區塊內**——與 `bounded-estimates`
既有的處理一致。能不能防止誤讀不是這條檢查能回答的。

**風險四：階段是手動切換的，可能忘記切。**
忘記切的方向是「停在較嚴的階段」，不是放行。這是決策 1 選擇宣告值而非
系統時間的直接後果，也是接受它的理由。
