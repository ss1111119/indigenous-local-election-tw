## Goals / Non-Goals

**Goals**

- 圖表的顏色差異與文字對比是**算出來的**，不是挑出來的
- 顏色以外至少還有一條取得數值的路徑，且該路徑在列印與高對比模式下仍存在
- 這些決定被測試釘住，不依賴下一個人讀過本文件

**Non-Goals**

- **不為其他圖表補替代表格**（性別方格、投票率折線等）。政黨圖是這次量測出問題的那一張；一次替全部加上 `<details>`，版面會多出五塊，那是設計決定不是無障礙決定，應分開判斷。
- **不把數值塞進 `aria-label`**。變成一長串無法導覽的朗讀內容，且與表格兩份資料要各自維護。
- **不加紋理／pattern 填充**。調整後 CVD ΔE 已過門檻（9.0／9.7），而紋理疊在 2px 間隙的細長條上只會更雜。若日後真的要黑白列印，再單獨評估。
- **不做 JS 動態亮度判斷墨色**。四個系列固定、政黨不會動態新增，跑一次算好寫進 CSS 變數即維護成本最低；瀏覽器端每次重算是為不存在的需求付代價。
- 不觸碰 `data/processed/` 與長表產生邏輯。

## 決策

### 1. 語意色不動，動的是「其他」桶與文字

政黨色相受現實慣例約束（藍＝國民黨、綠＝民進黨），改動會造成讀者認知錯位。「其他各政黨」是彙總桶，**沒有對應的現實色**，所以調整集中在它身上：淺色調亮、暗色壓暗，兩邊都把與綠的距離推過門檻。

暗色的民進黨綠做了 `#199e70`→`#1da77a` 的同色相微調，因為暗底下光調灰無法同時滿足亮度帶與門檻。

### 2. 對比不足時改文字墨色，不改語意色 —— 本輪一度做錯

實作過程中曾把淺色國民黨藍 `#2a78d6` 改成 `#2670cc`，只為了讓段內白字從 4.42:1 推到 4.92:1。**這是錯的**，且違反決策 1：原色配**純黑**是 4.76:1，本來就合格。已退回原色並改用 `--lab1:#000`。

留下這段記錄是因為誘因會重現——遇到「差一點就過」時，改填色比改文字看起來更順手。規則是：**強語意色遇到對比不足，先窮盡文字的黑白兩種選擇。**

### 3. 每系列一個墨色變數

`--lab1`～`--lab4` 與 `--s1`～`--s4` 一一對應，`PARTIES` 陣列的每一項同時帶填色與墨色變數名。八組實測值：

| | 系列 | 填色 | 墨色 | 對比 |
|---|---|---|---|---|
| 淺 | 國民黨 | `#2a78d6` | `#000` | 4.76 |
| 淺 | 無黨籍 | `#eb6834` | `#16181A` | 5.56 |
| 淺 | 民進黨 | `#1baf7a` | `#16181A` | 6.32 |
| 淺 | 其他 | `#ADB3B9` | `#16181A` | 8.41 |
| 暗 | 國民黨 | `#3987e5` | `#16181A` | 4.89 |
| 暗 | 無黨籍 | `#d95926` | `#16181A` | 4.58 |
| 暗 | 民進黨 | `#1da77a` | `#16181A` | 5.82 |
| 暗 | 其他 | `#6A7178` | `#fff` | 4.95 |

暗色主題有三個系列用近黑墨色、一個用白，看似不一致，但那是各自填色亮度決定的結果，不是風格選擇。

### 4. 替代內容用可展開表格，不是視覺隱藏表格

視覺隱藏（`sr-only`）只服務螢幕閱讀器。可展開的 `<details>` 成本相同，但同時解決：鍵盤使用者取得窄段數值、列印時保留完整數字、高對比／灰階下不依賴顏色、以及一般讀者想抄數字。

表格由**同一份 `DATA` 常數**產生，不是另一份手抄資料——否則就是重新製造這個專案已經修過兩次的漂移。

### 5. 高對比模式保留圖表原色

`forced-colors: active` 時系統會覆寫填色，四個系列會塌成同一色，圖表歸零。既然顏色在此承載資料，對 `svg`／`.sw`／`.pty` 設 `forced-color-adjust:none`；頁面其餘部分照樣交給系統。同時因為決策 4 已提供表格，即使這個判斷在某些平台失效，資訊仍取得到。

### 6. 列印一律套淺色

瀏覽器列印預設剝除背景色。暗色主題下白字會印在白紙上完全消失，長條圖也可能被省墨規則吃掉。`@media print` 直接覆寫變數為淺色一組，並以 `print-color-adjust:exact` 保住色塊。

驗證方式受限：無法直接截圖列印結果，改以「把 `@media print` 換成 `@media screen` 的暫時副本、並強制頁面處於暗色主題」渲染，確認變數確實被覆寫（實測段內數字為 `rgb(0,0,0)`、底色 `#fff`）。

`forced-colors` 只驗到 CSS 規則正確解析，**沒有在真實 Windows 高對比模式下確認**。

### 7. 一致性要有東西在守，不是有指令可查

原本這條決策寫的是「`--check` 早就在報 36 項差異，但沒人跑，所以錯誤數字在站台上活了一整天」。**那個判斷是錯的，留在這裡當記錄。**

實際情形：HEAD 的產生器只比對政黨名稱字串，站台常數與它完全一致（同日 12:52 與 13:2x 兩次 `--check` 都通過）。那 36 項差異是 16:21 之後才出現的——另一個同時進行的 change（`fix-party-bucket-drift`）把分桶規則改成 (政黨代號, 政黨名稱) 配對，舊屆的無黨籍才歸位。我看到 `--check` 失敗就推論成「公開站台的數字錯了」，**沒有先問這個失敗是什麼時候開始的**，接著跑了 `--write`，把別人進行到 3/11 的成果寫進站台檔案。

修正後的理由反而更強，而且是兩層：

1. **產生邏輯改動當下就該有訊號。** 若這個測試早已存在，`fix-party-bucket-drift` 一改分桶規則，測試立刻失敗並列出差異的鍵——那是正確且無歧義的訊號（「產生器變了，站台要重新產生」），不會被誤讀成「站台資料壞了」。
2. **誤讀的代價是真實的。** 我因為誤讀而在別人的工作檔上跑了寫入指令。測試不會阻止那件事，但會讓「這是誰的改動、什麼時候開始的」在第一時間就清楚。

同理，配色與墨色的決定若只寫在本文件，下一個人看到四個只用於一處的 CSS 變數，很可能當成冗餘而移除，然後白字回來、對比掉回 2.12:1，且**沒有任何測試會失敗**。所以對比下限也進測試。

**跑會寫檔的指令前先看 `git status` 有沒有自己不認識的改動**——這一條沒辦法用測試守，只能寫在這裡。

### 8. 顏色可及性只放一個 capability

`fix-party-bucket-drift` 在 `site-data-generation` 下也加了一條 `Colour Is Not The Only Encoding`，與本 change 的 `Color-Encoded Data Has A Tabular Equivalent` 是同一件事的不同切面。兩個 change 若各自歸檔，`openspec/specs/` 會出現「顏色可及性一半在資料產生能力、一半在圖表可及性能力」，下一個人無從判斷該遵守哪一條。

分工定為：**顏色編碼與可及性一律歸 `site-chart-accessibility`**；`site-data-generation` 只負責「由長表產生內嵌常數」這件事本身。理由是後者的 Purpose 與其餘 requirement 全是產生流程，顏色不在其範圍。

該 change 提出的兩點比本 change 原本的寫法嚴格，已吸收進 `site-chart-accessibility`：

1. **慣用色不外借**——本 change 原本只寫「慣例色不要動」，沒有禁止把政黨色**指派給不是該政黨的桶**。少了這條，「把其他桶改成綠色以拉開與灰的距離」在形式上是合規的，而那顯然錯。
2. **驗證須留紀錄**（工具、模擬的色盲類型、門檻、實測值）——本 change 的 design 有這些數字，但 spec 沒要求下一個人也提供。

因此請 `fix-party-bucket-drift` 從它的 `site-data-generation` delta 移除 `Colour Is Not The Only Encoding`；內容已在此保留，未遺失。**本 change 不去修改另一個進行中 change 的檔案**——那正是本輪 `--write` 事故的同一類錯誤。

### 9. 量測工具必須在 repo 裡

決策 8 吸收進來的 `Color Verification Is Recorded, Not Asserted` 要求記錄「所用工具」。但本 change 實際用的是 `dataviz` skill 的 `validate_palette.js`——**它不在版控內，另一個並行 session 明確回報找不到它**（repo、`.claude/skills/`、`~/.claude/` 都沒有）。要求別人記錄一個他們拿不到的工具，等於那條 requirement 沒有人履行得起。

因此在 repo 內實作 `scripts/palette_metrics.py`，並對照外部驗證器校準：

| 量測 | 參考值 | 本實作 | 差 |
| --- | ---: | ---: | ---: |
| 常人 ΔE（兩組） | 16.9 / 16.6 | 16.9 / 16.6 | ≤0.04 |
| protan ΔE | 9.0 | 9.0 | 0.01 |
| deutan ΔE | 9.7 | 9.7 | 0.03 |
| tritan ΔE（兩組） | 9.6 / 15.1 | 13.9 / 32.9 | 4.3 / 17.8 |

前三項吻合到小數點，是因為找出了對方的做法：**Machado 2009 的 severity 1.0 矩陣、套用在線性 RGB**（改在 gamma 空間會差 0.6~1.2）。

**tritan 沒有實作。** 試過 Viénot 單平面近似與 Machado 矩陣都對不上，對方顯然用別的方法（可能是 Brettel 雙平面）。提供一個差 18 的數字比不提供更糟——它會讓人以為量過了。本專案 spec 的 CVD 門檻只涵蓋 protan 與 deutan，所以這個缺口不影響 requirement 的可履行性；需要 tritan 就得用外部驗證器，且要標明來源。

順帶補上本 change 原本的缺口：色差先前**沒有任何測試**在守（只守文字對比），所以把「其他」改成與鄰接系列糊在一起的顏色不會有人發現。`test_series_palette_separation` 補上這一層，也讓 `fix-party-bucket-drift` 的 4.1（無黨籍改中性深色，會產生兩個相鄰中性色）改完就有客觀判準。
