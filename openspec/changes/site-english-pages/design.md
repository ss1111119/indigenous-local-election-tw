## Context

站台三頁全中文。`docs/index.html` 與 `docs/legislative.html` 的資料常數
已由 `scripts/build_site_data.py` 以標記行就地替換產生（`DATA`、`LEG`、`BOUNDS`），
`docs/roster.html` 另有 `D` 與 `MAIN`。

實測可翻譯的量：

| 頁面 | HTML 內文 | JS 裡的字（圖表標籤、tooltip、限定語） |
| --- | ---: | ---: |
| `index.html` | 2,179 字 | 816 字 |
| `legislative.html` | 1,019 字 | 501 字 |
| `roster.html` | 462 字 | 407 字 |

資料側需要英譯的標籤：選舉種類名稱 11 個、政黨桶名 7 個、界限表出現的
政黨全名 45 個——但**實際顯示在界限面板上的只有 8 個**（各屆各門檻前四名），
其餘 37 個只在展開的完整表格裡。

英文頁一開就會受四條既有需求約束：`site-data-generation`（常數由腳本產生）、
`site-multi-dataset`（限定語與數字同一個可複製區塊）、`bounded-estimates`
（涵蓋率先於任何百分比）、`election-period-publication`（每一頁都要有判定紀錄、
選舉期間保留的歷史資料要標示不代表本屆）。

## Goals / Non-Goals

**Goals:**

- `docs/en/index.html` 與 `docs/en/legislative.html` 兩頁可讀、數字與中文版一致
- **限定語只有一份來源**，中英兩版都由它產生
- 顯示標籤的英譯逐項宣告，並註明是官方用法還是本專案自訂
- 「翻譯弱化了限定語」是**會失敗的檢查**，不是靠人看

**Non-Goals:**

- 不做 `roster.html` 的英文版（4,607 個人名，音譯無權威來源）
- 不英文化長表欄位名
- 不新增任何指標；界限的凍結對英文頁一樣有效
- 不做語言自動偵測或轉址——GitHub Pages 是靜態站，沒有伺服器端可做這件事，
  硬用 JS 轉址會讓分享連結指向讀者未必想要的語言

## Decisions

### 決策 1：限定語是**資料**，由產生器輸出，不是頁面裡的靜態文字

涵蓋率、「不是全體原住民」、「不代表本屆」這些句子，中英兩版都由
`scripts/build_site_data.py` 產生，以標記行寫入。

理由：這是本變更最重要的一條。限定語是這個專案的主要價值，
而它同時也是**最容易在翻譯時被弱化的東西**——譯者（包括我）會下意識
把「這不是全體原住民的政黨傾向」翻得比較順、比較短，順帶把限定拿掉。
把它變成產生的資料，兩版就不可能各自漂移。

具體形狀：`scripts/build_site_data.py` 增加 `STRINGS` 宣告，
`{key: {"zh": ..., "en": ...}}`，兩版頁面各有一行 `const T = ` 標記行。

**（2026-08-23 實作時擴大範圍）** 原本只打算收限定語，實作時發現 JS 裡還有
tooltip、表頭、`aria-label` 等 UI 文字。把它們一併收進 `STRINGS` 之後，
**兩版頁面的 JS 完全相同、只有 `T` 與 `L` 不同**——圖表程式碼不可能在
兩個語言間漂移。這比原訂範圍大，但風險更低：原訂做法會產生兩份各自演化的
繪圖程式碼，而那正是本專案在名錄的 `MAIN` 上踩過的坑。

⚠️ **靜態 HTML 裡的限定語不走 `T`。** 交給 JS 注入會讓「沒有 JS 就沒有
限定語」，而限定語是這個專案的主要價值、不能依賴腳本執行成功。
那些文字留在 HTML 原始碼裡，改由 `check_static_qualifiers()` 斷言它與
`STRINGS` **逐字相同**——單一來源的效果一樣達到，且限定語在原始碼裡看得到。

**替代方案**：英文頁的文案直接寫在 HTML 裡，靠人維護。否決——
那正是站台常數在改由腳本產生之前的狀態，也正是它落後資料集四屆的原因。

### 決策 2：標籤英譯逐項宣告，且**每一項都要標出處**

`LABELS_EN` 宣告表，每一項附 `source` 欄，取值為：

- `cec`：中選會英文站可查證的用法
- `common`：政黨自己的英文名（如 Democratic Progressive Party）
- `project`：**本專案自訂**，沒有找到官方或通行英文名

⚠️ 中選會英文站的頁面是 JS 渲染的，`WebFetch` 讀不到本文（與先前查
政府資料開放授權條款時同一個限制）。可查證到的只有搜尋摘要顯示的
"Lowland and Highland Indigene Legislator" 一類用法。因此
**大部分選舉種類名稱會是 `project`**，而那必須在頁面上說出來，
不能讓讀者以為那是官方譯名。

**替代方案**：全部自己翻、不標出處。否決——這個專案對「數字的出處」
要求到寫進 spec，對「名稱的出處」不該用另一套標準。

### 決策 3：界限面板只翻**顯示得到**的 8 個政黨，其餘保留原文並說明

展開的完整表格裡有 37 個小黨（臺灣雙語無法黨、小民參政歐巴桑聯盟、
制度救世島…），多數沒有通行英文名。這些在英文頁**保留中文原名**，
並在表格上方說明「沒有官方英文名者保留原文」。

理由：造 37 個英文名，讀者無從判斷哪些是真的。保留原文至少是誠實的，
而且那些政黨的得票率都在 1.5% 以下，不影響讀者理解主要結論。

**替代方案**：音譯或直譯全部 45 個。否決——與 `roster.html` 不做的理由相同。

### 決策 4：語言切換是**明確的連結**，不是自動偵測

兩版頁首互相連結（`hreflang="zh-Hant"` / `hreflang="en"`），不做
`navigator.language` 轉址。

理由：靜態站沒有伺服器端可做內容協商；JS 轉址會讓分享出去的連結
指向讀者未必想要的語言，而且會在返回鍵上打架。

### 決策 5：英文頁一樣要通過既有的四條需求，且**用同一組檢查**

不為英文頁另寫一套檢查。既有的檢查改為對「頁面清單」逐頁跑：

- `check_publication_record()` 已經是掃 `docs/*.html`——要改成**遞迴**，
  否則 `docs/en/` 下的兩頁會漏掉，而漏掉正是那條檢查要擋的東西
- `PAGES_REQUIRING_NOTICE` 增加兩個英文頁
- 界限區塊的涵蓋率順序檢查對英文頁同樣要跑

⚠️ 這一條有個真實的陷阱：`check_publication_record()` 目前用
`(ROOT / "docs").glob("*.html")`，**不含子目錄**。加了 `docs/en/` 之後
它會安靜地少檢查兩頁而不報錯——那正是「涵蓋檢查自己漏掉」的形態。

## Implementation Contract

**Behavior（做完之後看得到什麼）**

- `docs/en/index.html` 與 `docs/en/legislative.html` 存在、可離線開啟、
  數字與中文版逐鍵相同。
- 兩版頁首互相連結，`<link rel="alternate" hreflang>` 兩個方向都有。
- 英文頁的界限區塊：涵蓋率（11.0%）與 "mountain indigenous townships"
  出現在該區塊任何百分比之前；限定語與數字在同一個 `.bnd` 區塊內；
  三個門檻並列。
- 英文頁帶 `CURRENT_TERM_NOTICE` 的英文版。
- `docs/發布判定紀錄.md` 有這兩頁的判定列。
- `docs/sitemap.xml` 列出五個網址。

**Interface / data shape**

- `STRINGS: dict[str, dict[str, str]]` —— `{key: {"zh": ..., "en": ...}}`，
  每個 key 兩種語言都必須有值。
- `LABELS_EN: dict[str, tuple[str, str]]` —— `{中文名: (英文名, 出處)}`，
  出處取值為 `cec` / `common` / `project`。
- 頁面標記行：`const T = `（文案）、`const DATA = ` / `const LEG = ` /
  `const BOUNDS = `（資料，與中文版相同的值）。
- `check_publication_record()` 改用 `rglob("*.html")`。

**Failure modes（都必須中止並具名）**

- `STRINGS` 有 key 缺 `en` 或缺 `zh` → 中止並列出該 key
- `LABELS_EN` 有項目缺出處或出處不在三個允許值內 → 中止並列出該項
- 頁面上出現未經 `LABELS_EN` 宣告的中文標籤（英文頁）→ 中止並列出
- `docs/` 遞迴掃描到的 HTML 未出現在判定紀錄 → 中止並具名（既有行為，
  但要確認遞迴之後仍成立）
- 英文頁缺 `CURRENT_TERM_NOTICE` 的英文版 → 中止並具名該頁

**Acceptance criteria**

- `python scripts/build_site_data.py --check` 對**五個**頁面全綠，
  且中文三頁的既有屆別仍逐鍵重現、位元組未變
- 英文頁與中文頁的資料常數**逐鍵相同**（同一份資料，不同語言）
- `pytest scripts/test_build_site_data.py` 通過，新增檢查不少於 12 項
- 變異全數被偵測，且至少包含：`STRINGS` 少一個 `en`、
  `LABELS_EN` 少一個出處、把 `glob` 改回非遞迴、
  英文限定語被翻得比中文弱（拿掉 "not the whole"）
- 每個被變異的檔各一個 canary

**Scope boundaries**

- 在範圍內：`docs/en/` 兩頁、`scripts/build_site_data.py` 的 `STRINGS` 與
  `LABELS_EN` 與遞迴掃描、兩份測試檔、`docs/sitemap.xml`、
  `docs/發布判定紀錄.md`、`README.md` 的線上瀏覽連結、中文兩頁的語言切換連結
- 不在範圍內：`docs/roster.html`（含其英文版）、長表欄位名、
  任何資料重建、任何新指標

## Risks / Trade-offs

**風險一：我是翻譯者也是審核者。**
沒有母語者覆核，英文的限定語可能讀起來比中文弱而我看不出來。
緩解是把限定語做成產生的資料並逐條列出中英對照，讓差異可被逐條檢視；
但這只讓問題**可見**，不能保證譯文夠強。這一點必須寫在頁面上：
英文版註明它是專案自譯、以中文版為準。

**風險二：`project` 出處的譯名會被當成官方譯名。**
標了出處也可能沒人看。緩解是英文頁在選舉種類第一次出現時附中文原名，
讓讀者至少能反查。

**風險三：多一個語言就多一份會過期的東西。**
限定語由產生器輸出解決了漂移，但頁面結構（章節順序、圖表數量）
仍是兩份 HTML。若日後中文頁增章而英文頁沒有，不會有任何檢查報錯。
本變更**不解決**這一點，只在紀錄檔寫明英文頁的基準版本，
讓下一個人知道要對齊什麼。

**風險四：選舉期間新增兩個公開頁面。**
依 `election-period-publication`，翻譯既有的凍結歷史數據不算新增
解讀性指標，所以規則允許。但它確實擴大了觸及範圍。
兩頁必須各自做判定並記錄，且界限的凍結對英文頁一樣有效。
